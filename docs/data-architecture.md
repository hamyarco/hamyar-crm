# فضای دادهٔ مشترک بین سایت و CRM

سه سرویس روی این سرور داده تولید می‌کنند: **سایت همیار** (وردپرس/ووکامرس/LearnDash روی
MariaDB میزبان)، **CRM** (ویتایگر روی MariaDB داخل داکر) و **Pulse** (داشبورد مدیر،
Next.js + Postgres). این سند می‌گوید داده چطور بینشان جابه‌جا می‌شود و چرا این‌طور.

## تصمیم اصلی: یک انبار، نه سه تا سینک دوطرفه

وسوسهٔ اول این است که سایت و CRM را مستقیم به هم سینک کنیم. این کار را نکردیم، چون سینک
دوطرفهٔ دو سیستم زنده یعنی قانون تعارض، حلقهٔ بی‌نهایت و داده‌ای که کسی نمی‌داند کدام
نسخه‌اش درست است.

به‌جایش: **Postgres داشبورد Pulse انبار مشترک است.** هر سیستم فقط خوانده می‌شود و
نتیجه‌اش در یک شمای ستاره‌ای می‌نشیند. هیچ‌کدام از دو سیستم عملیاتی از این مسیر نوشته
نمی‌شوند.

```
  سایت همیار (MariaDB میزبان)  ──read-only(hamyar_ro)──┐
                                                        ├──► Pulse Postgres ──► داشبورد
  CRM ویتایگر (MariaDB داکر)   ──read-only(pulse_ro)───┘      core / kpi / ops
```

## انبار هیچ اطلاعات شخصی نگه نمی‌دارد

این قاعده از قبل در Pulse بود و رعایتش کردیم: `core.dim_customer` شماره تلفن ندارد، فقط
`phone_hash` دارد — یعنی `sha256(phone)` و ۳۲ کاراکتر اولش. پس در انبار نه شماره هست نه
ایمیل نه نام.

همین ما را به کلید اتصال می‌رساند.

## کلید اتصال: شمارهٔ موبایل، بعد از یکسان‌سازی

اینجا تنها جای واقعاً ظریف کار است. دو سیستم یک شماره را دو جور می‌نویسند:

| | شکل ذخیره | تعداد |
|---|---|---|
| سایت (`nooshika_phone_num`) | `+989121234567` (E.164) | ۱٬۰۰۴٬۹۵۸ ایرانی + ~۱۳ هزار خارجی |
| CRM (`vtiger_leadaddress.mobile`) | `09121234567` | ۲۳٬۷۹۴ از ۲۴٬۳۲۳ لید (۹۷٫۸٪) |

خبر خوب: **هر ۲۴۳۲۳ لید CRM شماره موبایل دارند** — بدون استثنا. پس کلید برای صد درصد
رکوردها موجود است.

`toE164()` در `src/sources/crm.ts` شمارهٔ CRM را به شکل سایت می‌برد و بعد **با همان تابع
هش سایت** هش می‌کند، پس دو طرف روی یک رشته می‌نشینند. تست‌شده روی: `09…`، `+98…`،
`0098…`، `98…`، ارقام فارسی `۰۹…`، ارقام عربی `٠٩…`، شماره با خط تیره، و شمارهٔ ده‌رقمی
بدون صفر. هرچه با اطمینان قابل تبدیل نباشد `null` می‌شود — **بهتر است یک لید بی‌تطبیق
بماند تا اینکه به آدم اشتباهی بچسبد.**

## چه چیزی وارد انبار می‌شود

| جدول | محتوا |
|---|---|
| `core.fact_crm_lead` | هر لید: تاریخ ساخت/ویرایش، وضعیت، منبع، مالک، تبدیل‌شده یا نه، `phone_hash`، و `customer_id` کاربر سایت بعد از تطبیق |
| `core.dim_crm_owner` | کاربران ویتایگر (فقط نام کاربری) برای اینکه بشود لید را به مالکش نسبت داد |
| `kpi.crm_lead` | ویوی ترکیبی: لید + مالک + کاربر سایت + اینکه آخرش خرید کرد یا نه |

`kpi.crm_lead` همان چیزی است که سؤال‌های بین‌سیستمی را جواب می‌دهد: «از لیدهای این ماه
چند درصد آخرش خرید کردند»، «لیدهای کدام کارشناس بیشتر تبدیل می‌شوند»، «لیدهایی که خرید
کردند از کدام کانال آمده بودند».

## اجرا

منبع `crm` در worker ثبت شده، هر **۳۰ دقیقه**، و روی `(modifiedtime, crmid)` جلو می‌رود —
پس لید ویرایش‌شده دوباره می‌آید و بار اول هم کل ۲۴ هزار لید را ۵۰۰۰تایی backfill می‌کند.

مهم: این منبع زیر **همان محافظ بار** بقیهٔ منبع‌هاست (`hostBusy()`). عصرها که موج پیامک
می‌رود و PHP اشباع می‌شود، sync خودش را عقب می‌کشد. همان سرور است، همان محدودیت.

تطبیق هویت در `derive()` انجام می‌شود، فقط روی لیدهای تطبیق‌نشده و هرکدام یک ایندکس‌لوکاپ.
اگر یک شماره روی دو حساب سایت باشد، کوچک‌ترین `id` برنده است تا جواب بین اجراها تغییر نکند.

## نوشتن در CRM — عمداً هنوز نه

مرحلهٔ بعدی که خواستی («دیتا از سایت برود توی CRM») نوشتن است، نه خواندن، و قاعده‌اش این
است: **حتماً از طریق API وب‌سرویس ویتایگر، هرگز SQL مستقیم.** اگر مستقیم در جدول بنویسیم
دسترسی‌ها و گردش‌کارها و event handlerها دور زده می‌شوند و اتوماسیون‌های خود CRM بی‌صدا
می‌خوابند. API فعال است و هر ۲۲ کاربر accesskey دارند (`docs/vtiger-development.md`).

پیشنهاد: اول یک‌طرفه سایت ← CRM، و اول در حالت خشک (فقط لاگ کند چه لیدی می‌ساخت) تا
ببینیم چند رکورد و با چه کیفیتی تولید می‌شود؛ بعد روشنش کنیم.

## راه‌اندازی

```bash
/opt/hamyar-crm/connect-pulse.sh
```

کاربر `pulse_ro` را با رمز تصادفی می‌سازد (فقط SELECT روی `vtiger.*`)، دیتابیس CRM را روی
`127.0.0.1:3307` منتشر می‌کند (فقط لوکال‌هاست؛ کانتینر دیتابیس ~۱۰ ثانیه ری‌استارت می‌شود)،
رمز را در `.env` داشبورد می‌گذارد و worker را بالا می‌آورد.
